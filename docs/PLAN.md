# Scam Shield — Project Plan & Architecture

> **Status (2026-10-18): built.** Everything below is implemented; see the [README](../README.md) to run it,
> [architecture.md](architecture.md) for how it works, and [results.md](results.md) for numbers.
> Where the build differs from this plan:
> - **Replay control lives in the CLI** (`tools/replayer/replay.py`), not a web button, because a Vercel app can't run it.
> - **No shadcn/ui.** A handful of Tailwind components matching the deck's palette were enough.
> - **Synthetic data generator added** (`ml/src/make_synthetic.py`). Real PaySim senders almost never repeat, so
>   per-customer reasons (new payee, unusual amount) can't be learned from it. PaySim is still supported as-is.
> - **SHAP comes from LightGBM's `pred_contrib`**, not the `shap` package (exact TreeSHAP, easier on s390x).
> - **IEEE-CIS audit is wired up but not yet run**: it needs the Kaggle files (`python ml/src/pipeline.py --ieee`).
> - **LinuxONE deployment and on-machine benchmarks are still to do**; they need the Community Cloud VM.

## Context
Team Inat (6 people) pitched **Scam Shield** for IBM Z Datathon 2026 (Real-Time AI for Critical Decisions): score every payment in milliseconds, explain why (reason codes), act (Allow / Verify / Hold), keep a human in charge of holds, log everything for compliance, warn customers in Tamil/English, and prove the model isn't using shortcuts. The repo (`e:\Self\misc\Projects\ScamShield`) is empty. This plan turns the deck into a buildable, production-shaped project that a student team can actually finish: **one Next.js app + Supabase**, plus the one piece that has to be Python — the ML scorer.

Promises from the deck that the build must back up with real numbers:
- recall at 1% false-positive rate
- p99 scoring latency, throughput (TPS)
- shortcuts recovered out of 10+ planted
- scorer deployed on IBM LinuxONE

## 1. Architecture at a glance

```
 ┌──────────────┐   POST /score    ┌────────────────────────────┐
 │  Replayer    │ ───────────────▶ │  Scorer (FastAPI, Python)  │  ← runs on LinuxONE
 │ (PaySim as a │ ◀─────────────── │  features → LightGBM →     │
 │  live stream)│   decision+why   │  SHAP reasons → policy     │
 └──────────────┘                  └─────────────┬──────────────┘
                                                 │ async write (not in hot path)
                                                 ▼
                                   ┌────────────────────────────┐
                                   │  Supabase                  │
                                   │  Postgres · Auth · Realtime│
                                   │  · Storage (model files)   │
                                   └─────────────┬──────────────┘
                                                 │ realtime subscription
                                                 ▼
                                   ┌────────────────────────────┐
                                   │  Next.js app (Vercel)      │
                                   │  Analyst dashboard,        │
                                   │  audit log, model report,  │
                                   │  customer payment demo,    │
                                   │  LLM warnings (server-side)│
                                   └────────────────────────────┘
```

**Key design choices (and why)**
- **Scorer is the only hot path.** Next.js is never between the payment and the decision, so p99 latency is honest and only measures feature lookup + model + SHAP + policy.
- **Persistence is async.** The scorer returns the decision immediately, then writes to Supabase in a background task. A DB hiccup never blocks a payment.
- **LLM is off the hot path.** Tamil/English warnings are generated by Next.js only when a "Verify" is shown, with pre-written template fallbacks. LLM output never decides anything.
- **Supabase Realtime** replaces a custom websocket server: the dashboard subscribes to new `decisions` rows.
- **Policy is config, not code.** Thresholds (`allow < 0.3 ≤ verify < 0.8 ≤ hold`) live in a YAML/env file and are versioned with the model.

## 3. Data & ML plan

**PaySim (primary, streamed)** — trains the live model.
Engineered features (all computable online from `state.py`):
- `is_new_payee` (first time this `nameOrig → nameDest`)
- `amount_vs_user_mean` (z-score vs. the sender's running mean)
- `hour_of_day` from `step`, `is_odd_hour`
- `balance_drain_ratio` (`amount / oldbalanceOrg`)
- `txn_velocity_1h`, `type` (TRANSFER / CASH_OUT …)
- Drop the leaky balance-error columns PaySim is known for (and document why — that's itself a shortcut story).

**IEEE-CIS (secondary, offline)** — used for the shortcut audit experiments and to show device/identity reason codes on the model page. Not streamed (different schema; don't try to merge datasets).

**Model** — LightGBM (fast, small, good on tabular, SHAP TreeExplainer is exact and fast). Time-based split (train on early steps, test on later) — no random split.

**Metrics written to `metrics.json`** → uploaded to Supabase `model_versions`:
recall@1%FPR, PR-AUC, chosen thresholds, confusion matrix per action.

**Shortcut audit**
1. `plant_shortcuts.py` creates a copy of the data with 10+ traps, e.g. a fake `device_type` that equals the label 90% of the time, an ID-prefix pattern, a timestamp leak, a constant-for-fraud merchant code, etc. Each trap is recorded in a manifest.
2. Train on the poisoned copy.
3. `shortcut_audit.py` runs permutation importance + feature masking + "drop-one, retrain, measure recall drop".
4. Report: traps recovered / planted, and accuracy drop per trap. Same audit run on the clean model must show no suspicious features → this is the "right for the right reasons" slide with real numbers.

## 4. Scorer service contract

`POST /score`
```json
// request
{ "txn_id": "…", "account_id": "C123", "payee_id": "M456",
  "amount": 48500, "type": "TRANSFER", "ts": "…", "old_balance": 52000 }
// response
{ "txn_id": "…", "risk": 0.92, "action": "hold",
  "reasons": [{"code":"NEW_PAYEE","weight":0.31}, {"code":"AMOUNT_SPIKE","weight":0.27}, {"code":"ODD_HOUR","weight":0.12}],
  "model_version": "lgbm-2026-10-20", "latency_ms": 3.4 }
```
- Reason codes are a fixed enum (`NEW_PAYEE`, `AMOUNT_SPIKE`, `ODD_HOUR`, `BALANCE_DRAIN`, `HIGH_VELOCITY`, …). Frontend maps codes → EN/TA text via `i18n/`. Never send prose from the scorer.
- `/metrics` exposes Prometheus-style histograms so p99 comes from the service itself, not guesswork.
- Account state is in-process (dict) for the demo; note Redis as the "real" swap-in.

## 5. Supabase schema (core tables)

| Table | Purpose |
|---|---|
| `transactions` | raw payment as received |
| `decisions` | risk, action, reasons (jsonb), model_version, latency_ms — **Realtime enabled** |
| `reviews` | analyst action on a held txn: release / keep_hold, who, when, note |
| `audit_log` | append-only: every decision + review with full inputs; insert-only via RLS, UPDATE/DELETE blocked by trigger |
| `model_versions` | metrics.json, thresholds, artifact path in Storage |
| `shortcut_audits` | audit run results per model version |
| `profiles` | user → role (`analyst`, `compliance`, `admin`) |

Auth: Supabase email login. RLS: analysts read decisions + write reviews; compliance read-only on audit_log; scorer writes with a service-role key held only on the server.

## 6. Next.js app — screens

1. **Queue** (`/queue`) — live list of Hold/Verify cards, newest first, Realtime-driven. Matches slide 8.
2. **Decision detail** (`/tx/[id]`) — risk bar, top reasons, account history mini-table, **Release / Keep hold** (server action → `reviews` + `audit_log`).
3. **Audit log** (`/audit`) — filter by date/action/analyst, CSV export.
4. **Model** (`/model`) — recall@1%FPR, p99, TPS, shortcut-audit table (planted vs. recovered).
5. **Customer demo** (`/pay`) — phone-sized mock payment; on Verify shows the "Hold on a moment" card in EN + TA from `/api/warnings`.
6. **Replay control** — start/stop stream, set TPS, for live demos.

LLM: Gemini or IBM Granite (check event rules), called server-side, input = reason codes + amount only (no PII), output cached per reason-combination; fallback to `i18n` templates if the call fails or times out (>1.5s).

## 9. Verification (definition of done)

- `pytest services/scorer` — schema, policy thresholds, reason mapping, feature parity test (training features == serving features for the same rows).
- `python ml/src/evaluate.py` prints recall@1%FPR on the time-held-out set.
- `python ml/src/shortcut_audit.py` prints `recovered X / 10+` on poisoned data, ~0 flags on clean data.
- Load test against LinuxONE scorer → p99 ms and sustained TPS saved to `docs/results.md`.
- End-to-end demo: start replay → cards appear in `/queue` within ~1s → release one → row appears in `/audit` with inputs → `/pay` shows Tamil + English warning for a Verify case.
- CI green: lint + typecheck (web), pytest (scorer), s390x image builds.
